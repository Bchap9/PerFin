# Release checklist (v1.0.0 verification run)

This is the end-to-end check run before tagging v1.0.0. Each step lists the
commands, the outcome and the evidence. Outcomes are **PASS**, **FAIL**, or
**NOT EXERCISED**, and every NOT EXERCISED step says why. Use the same steps
for later releases. Replace the scratch paths with your own, and run against
the image the release workflow built, not a local variant.

Run on 2026-11-04, working tree on branch `claude/inspiring-mccarthy-ln0dea`
(base commit `c57c564` plus the uncommitted Phase 7 work). Docker 29.9.2,
Linux 6.18 with Landlock. All data is synthetic and generated by
`backend/tests/fixtures/synth_*.py`. The stack used a generated `.env` in a
scratch directory, never in the repository.

## 1. Build the image

**Shipped Dockerfile, in this sandbox: FAIL (environment).**

```sh

  --build-arg NODE_IMAGE=local/node-ca:22-alpine \
  --build-arg PYTHON_IMAGE=mirror.gcr.io/library/python:3.12-slim \
  --build-arg UV_IMAGE=local/uv:0.11.32 -t perfin:shipped-attempt .
```

The sandbox re-terminates TLS with its own CA, so `uv sync` failed with
`invalid peer certificate: UnknownIssuer` in a base image without that CA.
The runtime stage's `apt-get update` cannot work here: `deb.debian.org` is
blocked (`403 Forbidden` from the egress proxy, `Could not resolve
'deb.debian.org'` without it).

**Labelled local variant: PASS.** The variant is generated from
`deploy/Dockerfile` by a script, and these are the only differences:

- The backend build stage uses a base that trusts the sandbox CA. This is a
  build stage only; the runtime stage still uses
  `mirror.gcr.io/library/python:3.12-slim`, and its CA bundle is identical to
  upstream (148 certificates).
- The Debian `apt-get` step is replaced by
  `COPY --from=ocrdata /usr/share/tesseract-ocr/5/tessdata` from an Ubuntu
  24.04 stage that installs `tesseract-ocr-eng tesseract-ocr-osd`.
  `libseccomp2` is already in the trixie base. No `apt-get upgrade` of the
  base is done.
- The image is labelled `org.perfin.variant=local-verification`.

All application layers (frontend build, `uv sync --frozen`, app code,
migrations, user 10001, entrypoint) are unchanged. The image runs as
`uid=10001(perfin)` and has `/usr/share/tesseract-ocr/5/tessdata/eng.traineddata`.
The image used for the run is `perfin:rv-local-fix`
(`sha256:f8cab0d3d44f…`); it was rebuilt after each code fix below.

**The shipped image is built and scanned by GitHub Actions**, not here:

## 8. Backup and restore into a fresh stack

```sh
dc stop proxy api worker               # quiesced: only db running
scripts/backup.sh --compose-dir "$STACK" --output-dir "$BACKUPS" --passphrase-file backup.pass
# fresh stack: own project name (COMPOSE_PROJECT_NAME=perfinrestore), subnets and ports, same .env secrets
docker compose -f "$STACK2/docker-compose.yml" up -d db
scripts/restore.sh --compose-dir "$STACK2" --passphrase-file backup.pass --check-all "$BACKUPS"/perfin-backup-*.pfbak
docker compose -f "$STACK2/docker-compose.yml" up -d
```

**Bug (fixed):** the first quiesced backup failed with:

```
service "api" is not running
perfin backup: ERROR: perfin backup-info failed
```

An online backup (api running) succeeded before the fix. After the fix the
quiesced backup succeeded.

**PASS.**

- **Backup:** audit chain verified (head seq 49, hash `b970934f…d78629b`),
  `pg_dump -Fc`, both document volumes archived, encrypted to a 563,414-byte
  `.pfbak` plus `.sha256`. The run printed the master key id
  `1eb2bc21f007a961` and the reminder that the key is not in the backup.
- **Restore:** in order, the checksum matched, the archive was authenticated
  and decrypted, the manifest and members were verified, and the master key
  matched. Then `pg_restore`, the document volumes, and `perfin migrate`
  (already at head). The audit chain was verified up to seq 49 and the
  manifest's head matched. `restore-check --check-all`: 4 blobs checked, 3
  documents compared, 0 failed.
- **Database comparison:** an SQL comparison of the source (quiesced) and
  the restored database gave identical output, 79 lines:
  - row counts of all 70 tables in `public`;
  - per-account ledger sum and count;
  - audit head seq and hash;
  - document count plus an MD5 over their SHA-256 values;
  - blob count and bytes.
- **Restored stack:** all services healthy, and the proxy answered on its
  own port. A login with the source password and TOTP enrollment
  (`mfa_required`, then verify) worked, and the display name was "Zebulon
  Quixley".
- **Restored data through the API:** transactions per account 21/514.90,
  20/161.15 (19 statement rows plus the planted -321.00) and 21/634.69.
  `GET /documents/{id}/download` for the PDF and OFX returned files whose
  SHA-256 equals the originals.
- `perfin audit verify` must run as the owner role (`dc run --rm migrate
  audit verify`, which reported 49 rows ok). Run in `api` it reports 0 rows,
  because the app role cannot read the audit log. That is by design;
  OPERATIONS.md uses `migrate`.
